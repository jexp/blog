== Java Bienen - Unterwegs im Linux Kernel mit eBPF

In dieser Kolumne steigen wir etwas tiefer ab in den Linux Kernel.
Normalerweise ist dieser ja Gerätetreibern, Speicher-, Prozess- und Thread-Management vorbehalten und Nutzercode hat dort aus Sicherheitsgründen nichts zu suchen.

.eBPF Logo
image::https://upload.wikimedia.org/wikipedia/commons/b/b0/EBPF_logo.png[]

Auf der anderen Seite ist der Kernel die richtige Stelle um systemnahes Monitoring und Performance-Messungen vorzunehmen.
Dazu gibt es seit langem (1992) ein System namens BPF (Berkeley Package Filter) das zur deklarativen Filterung und Analyse von Netzwerkpaketen (in der OSI Schicht 2) genutzt werden konnte, zum Beispiel von tcpdump und wireshark.

Sogenannte BPF "Probes" (Sonden) wurden als Filterregeln geladen und mit ihnen Netzwerkpakete in einer simplen BPF-VM im Kernel ausgewertet.

Aber es war in seinen Fähigkeiten ziemlich beschränkt, so dass 2014 (Kernel 3.18) damit begonnen wurde, eine erweiterte Variante zu entwickeln "extended" BPF [eBPF], die nicht nur weitere APIs und Funktionen für Messungen sondern auch eine Programmiersprache enthielt, die im Kernel ausgeführt werden kann.

////
Software defined infrastructure for networking
get it into the linux kernel -> BPF -> extend -> bastardized version of BPF 
convinced Torvalds - "a better BPF" -> new features through backdoor
////

Auch die Arten von Ereignissen wurde deutlich erweitert von Netzwerkpaketen zu Speicherallokationen, Pagefaults, Dateizugriffe, Systemaufrufen, Stromversorgung und vieles mehr.
Die eBPF Programme laufen an der Schnittstelle zwischen Kernel und der Hardware, so dass Entscheidungen sehr früh in der Verarbeitung getroffen werden können, oder sogar auf den Geräteprozessoren (wie Netzwerkkarten mit XDP).
Ein Artikel beschrieb es als: "eBPF ist für Linux was CRISPR für Genetik darstellt".

Die Programme im User-Space können dann mittels Tracepoints, Interrupts und geteilten Datenstrukturen mit den eBPF Programmen kommunizieren.

Das ist ein Punkt, der normalerweise unter Sicherheitsaspekten undenkbar ist - Nutzercode im Betriebssystemkern auszuführen. 
Das würde zu viele Türen öffnen, sowohl für Missbrauch als auch Fehlverhalten das zur Instabilität für das ganze System führen würde.

Deshalb gibt es doch extra die Trennung zwischen Kernel- und User-Space, damit das nicht möglich ist, und Änderungen am Kernel nur durch geladene Kernel-Erweiterungen oder Code-Änderungen möglich sind, und natürlich der dafür notwendigen Neu-Übersetzung und Neustarts.

eBPF nutzt hier Ansätze wie Java, wir sehen viele Gemeinsamkeiten, auch aus ähnlichen Anforderungen heraus.
Modernes eBPF nutzt sogar eine Technology mit demselben Slogan "CO-RE: Compile Once Run Everywhere".

Programme werden als ein interpretierbarer bzw. compilierbarer Bytecode bereitgestellt.
Für diesen wird zuerst durch einen Verifikationsprozess [eBPF-Verifier] sicher gestellt, dass der Code valide und sicher ist (daher ist die Sprache auch nicht Turing-complete).

In der eBPF Welt wir das zwar eher mit JavaScript verglichen: "What Javascript is to the Web, eBPF is to the OS", aber die Konzepte sind dieselben.

Er prüft unter anderen:

* dass der Code nicht zu viele Instruktionen enthält, 
* terminiert, 
* nicht rekursiv ist
* keine unerlaubten Systemaufrufe oder Speicherzugriffe vornimmt 
* nicht zu lange läuft (effiziente Verarbeitung nötig)

== Anwendungsfälle

Es gibt für eBPF viele Anwendungsfälle, hier ist eine kurze Übersicht.
Die meisten großen Infrastruktur-Unternehmen (Netflix, Google, Cloudflare, Meta) setzen es aufgrund der Effizienz, Sicherheit und Flexibilität in Produktion ein.

* Netzwerkfilter - früh in Verarbeitung (ggf. auf NIC) Filter und Analyse von Netzwerkpaketen, Traffic-Shaping, Inhalte filtern, für ein- und ausgehenden Verkehr
* Observability - Traffic von jedem Device und das Verhalten von Prozessen darstellen auch besonders für Microservices, Anomalien, besser als Sidecars da im Kernel
* Security Policen - Prozesse überwachen, beenden, Verhalten beschränken, Netzwerkpakete filtern
* Power Monitoring - z.B. Batterieüberwachung in Android + Prozessverbrauch
* Eigene Erweiterungen und Logic für Eingabegeräte wie Tastaturen oder Touchscreens
* Scheduler Optimierungen Integration von Lastüberwachung in Thread-Scheduler-Entscheidungen
* Hotfixes, Workarounds, Hot Deployments für Kernel Funktionen
* Schnellere und einfachere Experimente mit neuen Ansätzen für Kernel-Funktionalität

eBPF Programme sind sehr low-level, nutzen also eine sehr minimale C-API, und sind reich an Bit-Operationen und primitiven Typen.

.Listing {listing} openat.bpf.c für das Tracing von "open" Systemaufrufen
[source,c]
----
#include <vmlinux.h>
#include <bpf/bpf_helpers.h>

SEC("tracepoint/syscalls/sys_enter_openat")
int trace_openat(struct trace_event_raw_sys_enter* ctx)
{
    u64 id = bpf_get_current_pid_tgid();
    u32 pid = id >> 32;

    // bpf_printk um die Prozess Information zur Trace Queue zu schicken
    bpf_printk("Process ID: %d enter sys openat\n", pid);
    return 0;
}

char LICENSE[] SEC("license") = "GPL";
----

== eBPF in Java

Normalerweise werden, wie im Beispiel gezeigt, eBPF Programme in C geschrieben und dann mittels des clang Compilers in Bytecode übersetzt.
Aber es gibt jetzt auch die Möglichkeit prototypisch eBPF Programme in Java zu schreiben. 

Johannes Bechberger, JVM-Entwickler bei SAP (SapMachine), hat mit seinem Projekt hello-ebpf gezeigt, wie das aussehen kann. Beim eBPF-Summit hat er dazu auch einen kurzen Vortrag gehalten [eBPF-Java-Agent] und auf vielen anderen Konferenz [Bechberger-Slides] auch.

Während das in der Realität wahrscheinlich noch eher selten passieren wird, ist es doch eine interessante Exploration, die Details besser verständlich macht.

Ein Anwendungsfall wäre, für Java Programme und besonders Bibliotheken Test-Setups für komplexe Nebenläufigkeits- (Deadlocks, Starvation, Race-Conditions), Netzwerk- (slow packets), oder Speicher- (Caches, CVEs) Probleme zu erzeugen, die die notwendigen Szenarien direkt erzeugen könnten.

Sein initiales Ziel war die Python BPF Compiler Collection (BCC) APIs in Java abzubilden, interessanterweise mittels Panama für das Foreign Function Interface (Java 21).

In der aktuellen Entwicklung ist BCC durch libbpf ersetzt worden.

Das Projekt kann mittels git gecloned werden und dann auf einer Maschine mit Linux 6.12 (oder neuer), mit aktiviertem eBPF und BTF gebaut werden, nachdem man die notwendigen Bibliotheken und Tools mittels `install.sh` installiert hat (siehe Listing {counter:listing}).
Alternativ kann das Setup auch auf anderen Betriebssystemen mit einer VM erfolgen, z.B. "Lima" wie in der Readme beschrieben.

Der Paketfilter (siehe Listing {counter:listing}) nutzt eine (von aussen zugreiffbare) Variable namens `count` um festhalten, wieviele Pakete schon im XPD-Filter vorbeigekommen sind. 
Jedes dritte (modulo 3) Paket wird dann nicht weitergeleitet, die mit `@BPFFunction` annotierte `shouldDrop` Methode wird geinlined.
Nach Installation des Programms kann dann von aussen ermittelt werden wieviele Pakete schon verarbeitet wurden.

.Listint {listing} Paketfilter, der jedes 3. Paket droppt
[source,java]
----
@BPF(license = "GPL")
public abstract class XDPDropEveryThirdPacket extends BPFProgram implements XDPHook {

    final GlobalVariable<@Unsigned Integer> count = new GlobalVariable<>(0);

    @BPFFunction
    public boolean shouldDrop() {
        return count.get() % 3 == 1;
    }

    @Override
    public xdp_action xdpHandlePacket(Ptr<xdp_md> ctx) {
        count.set(count.get() + 1);
        return shouldDrop() ? xdp_action.XDP_DROP : xdp_action.XDP_PASS;
    }

    public static void main(String[] args) throws InterruptedException {
        try (XDPDropEveryThirdPacket program = BPFProgram.load(XDPDropEveryThirdPacket.class)) {
            program.xdpAttach(NetworkUtil.getNetworkInterfaceIndex());
            while (true) {
                System.out.println("Packet count " + program.count.get());
                Thread.sleep(1000);
            }
        }
    }
}
----

=== Hinter den Kulissen

Erweiterungspunkte werden aus Interfaces, wie `SystemCallHooks`,`XDPHook` oder `Scheduler` übernommen, es reicht die Callback-Methoden zu implementieren. Der Java Code des BPFProgram's wird nach BPF-C übersetzt und dann mittels `clang` weiter nach Bytecode. Das passiert mittels eines Annotation Prozessors und Java-Compiler Plugins welches versucht die Semantik von Java möglichst nach C zu übertragen. Der übersetzte Bytecode wird von `libbpf` im Kernel nach Verifikation in die jeweiligen Erweiterungspunkte installiert.

Es ist von BPFProgram abgeleitet, einer umfangreiche Superklasse, die die Infrastruktur für die Definition und Management von eBPF Hooks und Datenstrukturen enthält inklusive BTF-Typen für den Datenaustausch mit dem Kernel und Bereitstellung BPF-Maps für den Datenspeicherung und Austausch mit dem Userspace Code (siehe `main`-Methode). Dazu gehört das Laden der Klasse, Installation und die Ausgabe im Terminal.

Es können auch klassische C-Programme innerhalb eines Java BPFPrograms spezifiziert und genutzt werden, diese werden dann als String übergeben.
Methoden und Klassen mit nur einem einzigen String Variablen Deklaration werden als C-Code interpretiert und übersetzt.

.Listing {listing} - Beispiel für HashMap für Statistiken und Datenaustausch
[source,java]
----
/**
 * Anzahl von openat System Aufrufen pro Prozess mittels einem HashMap Counter
 */
@BPF
public abstract class HashMapSample extends BPFProgram implements SystemCallHooks {

    // fixe Schlüssellänge
    private static final int TASK_COMM_LEN = 16;

    // Map definiert mit fixer Schlüsselänge und Integer ohne Vorzeichen
    @BPFMapDefinition(maxEntries = 256)
    BPFHashMap<@Size(TASK_COMM_LEN) String, @Unsigned Integer> map;

    @Override
    public void enterOpenat2(int dfd, String filename, Ptr<open_how> how) {
        @Size(TASK_COMM_LEN) String comm = "";

        // Aktuellen Prozess Name lesen 16 bytes in den String
        bpf_get_current_comm(Ptr.of(comm), TASK_COMM_LEN);

        // incrementiere Counter bei map[comm]
        Ptr<@Unsigned Integer> counter = map.bpf_get(comm);
        if (counter == null) {
            map.put(comm, 1);
        } else {
            counter.set(counter.val() + 1);
        }
    }

    public static void main(String[] args) throws InterruptedException {
        try (HashMapSample program = BPFProgram.load(HashMapSample.class)) {
            program.autoAttachPrograms();
            while (true) {
                System.out.println("OpenAt's per process:");
                for (var entry : program.map) {
                    System.out.printf("%16s: %4d\n", entry.getKey(), entry.getValue());
                }
                Thread.sleep(1000);
            }
        }
    }
}
----

HashMaps werden mit Schlüsseln mit einer fixen Länge (oder numerischen Werten) konfiguriert, haben eine Maximalzahl von Einträgen und reguläre Methoden zum Lesen (`bpf-get`) und Schreiben (`put`) von Einträgen. Die Aktualisierung von Werten erfolgt indirekt über Pointer auf sie.
Sie werden, genau wie Structs hinter den Kulissen konfiguriert und initialisiert.

Map's können als Datenaustauschmechanismus dienen, in unserem User Space Code können wir mittels Systemaufruf auf eine Kopie der Map des BPF Programms zugreifen und auslesen.

@BPF(license = "GPL")
@Property(name = "sched_name", value = "minimal_scheduler")
public abstract class MinimalScheduler extends BPFProgram implements Scheduler {
    // Queue ID
    private static final int SHARED_DSQ_ID = 0;

    // Neue Warteschlange in init erzeugen
    @Override
    public int init() {
        return scx_bpf_create_dsq(SHARED_DSQ_ID, -1);
    }

    // Prozess wird in Warteschlange gestellt zum späteren Ausführen 
    @Override
    public void enqueue(Ptr<task_struct> p, long enq_flags) {
        // Beschränkte Maximale Länge Ausführungszeit (jeder Prozess bekommt gleiche Laufzeit)
        // skaliert mit der Anzahl der wartenden Prozesse, damit das System benutzbar bleibt
        var sliceLength = ((@Unsigned int) 5_000_000) / scx_bpf_dsq_nr_queued(SHARED_DSQ_ID);
        scx_bpf_dispatch(p, SHARED_DSQ_ID, sliceLength, enq_flags);    }

    // Prozess von Warteschlange ausführen
    @Override
    public void dispatch(int cpu, Ptr<task_struct> prev) {
        scx_bpf_consume(SHARED_DSQ_ID);
    }

    public static void main(String[] args) throws Exception {
        try (var program = BPFProgram.load(MinimalScheduler.class)) {
            // In sched-ext installieren
            program.attachScheduler();
            // warten
            System.in.read();
        }
    }
}

I decided to write bindings using the new Foreign Function API (Project Panama, preview in 21) and bcc, the first and widely used library for eBPF, which is typically used with its Python API and allows you to write eBPF programs in C, compiling eBPF programs dynamically at runtime.

The main goal is to provide a library (and documentation) for Java developers to explore eBPF and write their own eBPF programs without leaving their favorite language and runtime.

The initial goal is to be as close to the BCC Python API as possible to port the book’s examples to Java easily. You can find the Java versions of the examples in the src/main/me/bechberger/samples and the API in the src/main/me/bechberger/bcc directory in the GitHub repository.

he API is purposefully close to the Python API and only deviates where absolutely necessary, adding a few helper methods to improve it slightly.

== Zukunft

eBPF wird zunehmend integraler Bestandteil moderner Betriebssysteme. 
Zukünftige Entwicklungen konzentrieren sich auf verbesserte Flexibilität, Modularität und Benutzerfreundlichkeit sowie Innovationen in Speicherverwaltung, Nebenläufigkeit und Integration mit User-Space-Anwendungen. Fortschritte wie dynamische Stacks, optimierte Observability-Tools und sicherere Programmterminierungen sollen eBPF zuverlässiger und vielseitiger machen, während neue Tools und Bibliotheken die Entwicklung erleichtern.
Mit dem aktuellen 6.12 Kernel ist auch das Scheduling jetzt erweiterbar (sched-ext), was viele neue Möglichkeiten eröffnet.
Wie Andy Pavlo diskutiert, auch bei der Weiterentwicklung von Datenbanken [eBPF-Databases] z.B. um Teile davon im Kernel laufen zu lassen.

== Fazit

eBPF ist ein mächtiges Werkzeug das im Linux-Observability Stack heutzutage einen festen Platz hat und gerade auch für Cloud-Deployments immer weiter ausgebaut wird.
Ohne einen Kernel neu zu compilieren oder Kernelmodule zu schreiben, können relevante Kernelfunktionalitäten effizient mit eigenem Code vorgenommen werden.
Viele Tools im Monitoring und Performance Bereich machen schon breite Nutzung von eBPF, durch die aktive Entwicklung ist da noch viel mehr zu erwarten.

Das Java-Projekt hello-ebpf ist schon heute mächtig, und macht die ePBF Programmierung für Java Entwickler zugänglicher.
Es wird spannend wie es sich weiterentwickelt und welche Rolle es in der zukünftigen eBPF Java Community spielen wird.
